## Запуск с PostgreSQL

1. Подготовьте **отдельную пустую PostgreSQL**. Не используйте рабочую БД команды для первоначального наполнения.
2. Создайте логин `naryadai_owner` с отдельным паролем, без прав суперпользователя, и базу `naryadai_production`, владельцем которой будет этот логин. Текущий сервер выполняет миграции; пользователю нужно владеть схемой и таблицами приложения.
3. Скопируйте `патч 1.4/server_config.production.example.json` в приватную папку **за пределами репозитория**, например `%USERPROFILE%\NaryadAI-private\server_config.json`.
4. Укажите настоящее `database_url`, URL Supabase, серверный ключ и существующее приватное хранилище фотографий. Для внешней БД включите TLS `sslmode=require`, лучше проверку сертификата `verify-full`; `prefer` в примере относится только к `127.0.0.1` на одном ПК.
5. Оставьте `seed_demo: false`. Пример временно отключает ИИ; для его запуска нужны ваши рабочие параметры AnythingLLM или обработчика. Удалённый обработчик требует `ai_mode: remote_worker` и отдельный `worker_token`.
6. В папке `патч 1.4` запустите `install.bat`, затем установите серверные зависимости и выполните первоначальную загрузку:

```powershell
& ".\.venv\Scripts\python.exe" -m pip install -r requirements-server.txt
& ".\.venv\Scripts\python.exe" tools/bootstrap_production.py --postgres-config "$env:USERPROFILE\NaryadAI-private\server_config.json" --credentials "$env:USERPROFILE\NaryadAI-private\accounts.csv"
& ".\.venv\Scripts\python.exe" run_server.py --config "$env:USERPROFILE\NaryadAI-private\server_config.json"
```

Инициализатор проверяет пустоту рабочих таблиц, сохраняет всё одной транзакцией и отказывается от повторной загрузки в наполненную БД. Данные не очищаются и демонстрационные записи не переименовываются в настоящие.
В существующей БД миграция 004 добавляет таблицы происхождения без удаления истории. Выключение демо-режима **не удаляет** уже импортированные демонстрационные записи: для чистого пилота создайте отдельную БД.

**Важно про фото:** в текущем PostgreSQL-адаптере снимки рабочих отчётов хранятся в Supabase Storage. Фото справочного датасета хранятся отдельно в этой папке; они не заменяют рабочие фото. Инициализатор может наполнить PostgreSQL без обращения к Storage, но для запуска API настройки Storage обязательны.

## Логины и пароли

Логины: `admin.01`, `manager.01`, `master.01`–`02`, `worker.01`–`15`.
Число аккаунтов соответствует стартовым слотам команды и требованиям кейса; это **не фактическая численность работников**.
ФИО полностью вымышлены, совпадения случайны. Источники подтверждают только названия должностей, а не личности. В логинах оставлены роль и номер. Ранее выданные пароли сохранены.
Каждому аккаунту генерируется собственный 32-символьный пароль криптографическим генератором; в БД хранится PBKDF2-хеш с индивидуальной случайной солью. Пароли `1234` в рабочем режиме не создаются.

CSV записывается только локально по явно указанному пути. Инициализатор запрещает хранение файла внутри репозитория и перезапись уже существующего CSV. Сбой вывода после успешного сохранения БД не уничтожает файл паролей.
Выбирайте приватную папку своего Windows-профиля: Unix-права `0600` сами по себе не настраивают Windows ACL. Файл не прикладывайте к PR, чату команды или общему диску. Выдайте каждый пароль его владельцу отдельно и отключите неиспользуемые аккаунты.
Политика создания/сброса пароля в рабочем режиме — минимум 12 символов.

Разряд `1` в наследуемой колонке — техническое значение старой схемы, **не установленная квалификация**. Новые профили помечаются `grade_confirmed=false`, интерфейс показывает «Не подтверждён», пока администратор явно не заполнит профиль. Смена, бригада и реальный человек аккаунта также требуют назначения.

## Первые реальные операции

1. Назначьте аккаунты конкретным пользователям, роли и доступы; подтвердите специальность и разряд.
2. Зарегистрируйте настоящее оборудование с инвентарными номерами, участком и критичностью.
3. Введите фактические смены и при необходимости бригады.
4. Проверьте модели материалов по паспортам оборудования, укажите цену по складскому документу. До подтверждения цены списание справочного материала блокируется; технический ноль не считается бесплатным материалом.
5. Мастер выбирает шаблон или создаёт наряд вручную, указывает настоящую заявку, оборудование, исполнителя и срок. Шаблон не заполняет реальные события, ремонт, норматив или выполненные часы.
6. Исполнитель прикладывает собственные фото и фактический отчёт. Решение о приёмке остаётся за мастером.

## Фотокаталог и обучение

См. [DATASET_CARD](photo_dataset/DATASET_CARD.md), [атрибуции](photo_dataset/ATTRIBUTIONS.md), [manifest](photo_dataset/manifest.json).
25 снимков: подшипники, передачи, трубы, конвейеры, насосы, сварка и другие компоненты. Часть примеров из велосипедной, авиационной и морской техники; перенос на оборудование предприятия требует проверки. Снимков АО «КМ», подтверждённых пар ремонта до/после и экспертно размеченных производственных отказов нет.

У каждой записи есть автор, источник и его ревизия, лицензия, изменения размера, SHA-256 и группа серии. Все записи изначально `annotation_status=unreviewed`, `training_approved=0`, `company_image=0`, `paired_photo_id=NULL`.
Модель **не обучена** автоматически. Перед обучением специалист должен разметить видимые дефекты, исключить неподходящие фото и проверить условия каждой лицензии; лицензии CC BY-SA требуют сохранения применимых условий распространения. Нельзя выдавать вывод модели за вывод NASA или предприятия.

```powershell
python photo_dataset/verify_dataset.py
python photo_dataset/export_training_split.py --annotations "C:\private\reviewed.csv" --output "C:\private\split.json"
```

Скопируйте `annotations.example.csv` в приватную папку. Эксперт заполняет `defect_visible=yes/no`, `defect_label`, `reviewer_code`, `evidence` и `review_status=expert_reviewed`. Неизвестные случаи остаются без допуска к обучению.
Экспортёр не принимает пустую разметку, дубли и менее трёх независимых групп; снимки одной серии целиком попадают только в train, validation или test. Это предотвращает утечку серии, но не подтверждает достаточный размер или качество набора для промышленного применения.

## Проверка локально без сервера PostgreSQL

Для проверки структуры и интерфейса можно отдельно создать SQLite-копию. Это не переключает работающий сервер:

```powershell
& ".\.venv\Scripts\python.exe" tools/bootstrap_production.py --sqlite-dir "$env:USERPROFILE\NaryadAI-private\sqlite-check" --credentials "$env:USERPROFILE\NaryadAI-private\sqlite-accounts.csv"
& ".\.venv\Scripts\python.exe" main.py --data-dir "$env:USERPROFILE\NaryadAI-private\sqlite-check"
```

Для переноса такой копии в отдельную пустую PostgreSQL инструмент `tools/migrate_sqlite_to_postgres.py` также переносит таблицы происхождения, шаблонов и фотокаталога. Справочные фото остаются файлами `photo_dataset/images`; их не нужно загружать как фото рабочих отчётов.

## Совместимость с хакатоном

Кейс требует демонстрационную историю минимум за три месяца с закономерностями. Чистая рабочая БД намеренно не выдумывает такую историю. Для защиты используйте **отдельную** демонстрационную БД: `run_demo.py`, `main.py --demo` или явное `seed_demo: true` на тестовом сервере. Импорт демо через API выключен в рабочем режиме.
Исторические демонстрационные архивы сохранены в репозитории для совместимости и не загружаются автоматически.
