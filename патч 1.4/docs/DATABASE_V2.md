# БД и интеграция — кейс №1 АО «Костанайские минералы»

Версия приложения 1.5, миграция `002`. Правила находятся в `app/case_store.py`, миграции — в `app/migrations.py` и `app/migration_v2_pg.sql`. Их используют SQLite и PostgreSQL; отдельный старый интеграционный патч больше не нужен после получения этой версии ветки.

## Что изменилось

- Выдача, принятие, очередь, отказ с причиной, начало, пауза, отчёт, проверка ИИ, закрытие и доработка. Коды `available/planned` означают выдачу без/с назначением; сохранены для совместимости. Приоритеты: `urgent/high/normal/scheduled` — аварийный, высокий, обычный, плановый.
- Фактические `issued_at/accepted_at/started_at/completed_at/closed_at`, типизированные события, причины и история назначений. Бригадный наряд резервирует время участников; ведущий указан в `worker_id`. Участник может отправить общий отчёт. Один закрытый наряд даёт один отчёт и результат бригады; объём не умножается на число участников.
- Историческая бригада записывается в назначении и отчёте. Перевод сотрудника сохраняет результаты прежней бригады. Отказы хранят своего автора и оценку мастера отдельно от текущего назначения.
- Выбор оборудования по ID/инвентарному номеру. Название оборудования может повторяться. Неизвестные новые названия отклоняются. Материалы нормализуются в единицы каталога; цена берётся из каталога на момент отправки и сохраняется в истории. Поддержаны г↔кг, мл↔л, см/мм→м, одинаковые единицы с/без точки. При преобразовании старых строк сохраняется общая стоимость.
- Отчёт без обязательного фото можно отправить на проверку и вернуть на доработку. Закрытие внеплановой работы без фото после запрещено. До пяти фото до и после; SHA-256, размер, время EXIF и предупреждения о повторе/старом фото. EXIF и совпадение изображения не доказывают подлинность ремонта; решение принимает мастер. Клиент уменьшает фото до 1600 px и удаляет лишние EXIF, включая GPS.
- Ночные смены хранят конец в часах относительно дня начала: 22→30 означает 22:00→06:00 следующего дня. Бронирования проверяются и на соседних датах.
- Пауза исполнителя и простой оборудования — разные записи. Простой явно открывается/закрывается; пересечения объединяются при расчёте часов.
- Порог непринятия: 10 минут, для аварийного — 3. Напоминание за 30 минут, просрочка повторяется каждые 30 минут. Уведомления доступны в приложении, есть подтверждение прочтения, дедупликация и очередь доставки. Не выдавайте наличие outbox за доставленный Android push.
- Одинаковый `request_id` с одинаковым содержанием возвращает тот же результат; другое содержимое получает 409. Изменение, события, уведомления и результат запроса фиксируются одной транзакцией. Фото загружаются до блокировки записи; при откате удаляются созданные объекты.
- PostgreSQL использует пул соединений. Чтение не берёт общий эксклюзивный advisory lock; короткие изменения пока сериализуются для защиты расписания между процессами. Это осознанный компромисс для MVP, его предел следует измерить на настоящем сервере.
- Панель по умолчанию передаёт активные наряды и 14 дней истории; архив доступен постранично. Статусы и свободное время вычисляются независимо от обрезанной страницы. CSV-экспорт получает весь архив. Есть сжатие HTTP и пакетная выборка оценок ИИ.
- Роль `manager` читает сводки без изменения нарядов. Чат мастера/руководителя/администратора получает проверенные недельные агрегаты и анонимные ID работников; произвольный SQL модель не выполняет. Для другого периода используйте API аналитики.

## Миграция существующей БД

Перед обновлением остановите старый сервер/клиенты и сделайте резервную копию PostgreSQL и приватного хранилища. При старте новая версия применяет `002` к старой SQLite, старой PostgreSQL или baseline `001`. Данные и пароли не заменяются демонстрационным набором. SQLite автоматически сохраняет `naryadai-before-v2.db`; миграция выполняет проверку внешних ключей и откатывается при ошибке. Сам файл фото остаётся в прежней папке.

Старые свободные названия импортируются в справочники с кодами `LEGACY-*`. Восстановленные времена отмечены `legacy_inferred/legacy_report_time`. Они не являются точным временем ремонта. Старые неполные принятые отчёты сохраняются как история; новое закрытие контролируется. Нельзя восстанавливать неизвестную причину отказа или фактический отказ оборудования из текста паузы.

Для переноса SQLite в **пустую** PostgreSQL:

```powershell
python tools/migrate_sqlite_to_postgres.py "путь/к/naryadai.db" --backup-dir "новая-папка-резервной-копии"
```

`DATABASE_URL` задайте локально в переменной окружения. Для облака нужен TLS. Инструмент делает копию SQLite вместе с фото и контрольными суммами, сохраняет ID и историю, отказывается смешивать пользователей с другой БД и не переносит активные сессии. Добавьте `--upload-photos` при настроенных `SUPABASE_URL/SUPABASE_SECRET_KEY/STORAGE_BUCKET`. Без этого флага файлы останутся в резервной копии, и их надо загрузить в приватный bucket отдельно. Запускайте перенос при остановленном приложении; после него проверьте вход, фото, наряд и сводку.

Для нового демонстрационного сервера используйте пакет `database/naryadai_database.zip` из корня репозитория: его импортёр устанавливает baseline, набор и миграцию 002. Версия набора v2 имеет другой ID и аккаунт `manager`; старый демонстрационный набор автоматически не подменяется.

## API для разработчика интеграции

Авторизация прежняя: `/api/login`, затем `Authorization: Bearer ...`.

| Метод | Назначение |
| --- | --- |
| `GET /api/catalogs` | Участки, оборудование, материалы, дефекты, бригады и нормативы |
| `GET /api/snapshot?day=2026-10-04&history_days=14&limit=500` | Панель, рейтинг, уведомления; `truncated` сообщает об обрезании |
| `GET /api/tasks?limit=100&offset=0` | Архив нарядов, `next_offset` |
| `GET /api/reports?limit=100&offset=0` | Архив версий отчётов |
| `GET /api/analytics?start=2026-09-01&end=2026-10-01` | Сводка; конец периода **не включён** |
| `GET /api/notifications` | Непрочитанные уведомления текущего пользователя |
| `POST /api/call/{method}` | Команда с `args/kwargs/request_id/photos` |

Фильтры аналитики: `site_id/equipment_id/worker_id/brigade_id`. Для смены передайте конкретные времена начала/конца, включая переход через полночь. Исполнитель получает собственный рейтинг. Новые команды: `reassign_task`, `change_priority`, `catalog_upsert`, `set_material_norm`, `set_employee_profile`, `start_downtime`, `end_downtime`, `assess_refusal`, `confirm_repeat`, `acknowledge_notification`. Сигнатуры находятся в `CaseWorkflow`; допустимые поля справочников перечислены в `catalog_upsert`.

Нормативы утверждает команда/ментор: `work_norms` задаёт тип оборудования/работы/дефект, часы и сложность, `material_norms` — расход в единицах каталога. При выдаче можно передать `norm_id` и `complexity`. Пустой каталог нормативов не заменяется выдуманными производственными нормами. ИИ получает только заданные нормативы, фото и технические предупреждения; имя модели, версия промпта, уверенность и качество 1–5 хранятся отдельно от решения мастера.

## Рейтинг

Предложенные командой разработки веса: качество 40%, своевременность 25%, отсутствие доработок/подтверждённых повторов 15%, объём с учётом сложности 15%, отсутствие необоснованных отказов 5%. Все компоненты возвращаются API. Объём нормируется к максимальному объёму работника в выбранном периоде/фильтре. Поэтому рейтинги разных периодов не являются абсолютной шкалой производительности. Непроверенный отказ не штрафует; повторная поломка штрафует только после подтверждения мастером связи с предыдущим ремонтом в течение семи суток. Без принятых работ рейтинг отсутствует. Рейтинг бригады агрегирует результаты по бригаде в отчёте, а не по сегодняшнему составу.

Число ремонтов не равно числу независимых физических отказов. Время `failure_at` и интервалы простоя фиксируются отдельно. Прогноз отказов, причинность и оценка качества настоящих ремонтов моделью требуют реальных данных и проверки; SQL-выборка кандидатов не доказывает вину сотрудника.

## Настройки и проверка

Новые поля серверного JSON: `database_pool_size` (1–32), `acceptance_minutes`, `urgent_acceptance_minutes`, `deadline_reminder_minutes`, `overdue_repeat_minutes`. По умолчанию 8/10/3/30/30. Для внешней доставки можно настроить `notification_webhook` (HTTPS) и `notification_webhook_key` (≥32 символа). Отправитель подписывает тело HMAC SHA-256 и передаёт `Idempotency-Key`; при сбое повторяет с задержкой, максимум восемь попыток. Получатель должен дедуплицировать событие. Реальный Android/FCM/Web Push провайдер подключается отдельно; без webhook работает внутренняя очередь приложения.

```powershell
pip install -r requirements-server.txt -r requirements-test.txt
python -m unittest discover -s tests -p "test_case1.py" -v
python -m unittest discover -s tests -p "test_photo_pipeline.py" -v
# После установки requirements.txt для Qt:
python -m unittest discover -s tests -p "test_case1_ui.py" -v
```

`TEST_DATABASE_URL` разрешён только для отдельной локальной тестовой PostgreSQL; тесты пишут синтетические строки. Скрипты `check_*.py` относятся к контракту прототипа 1.4 и его старым фикстурам; актуальные регрессии изменения находятся в `test_case1*.py`. Не запускайте тесты против рабочей БД.

Локальная проверка использует SQLite и PGlite 0.5.8 через psycopg/HTTP. Проверки ограничений SQL выполняются непосредственно в PGlite: его socket-адаптер имеет проблему восстановления после ошибки SQL. Настоящая PostgreSQL, несколько одновременных серверных процессов, p95 в облаке, восстановление PostgreSQL/Storage, мобильная доставка и точность модели здесь не подтверждены. Для промышленной эксплуатации нужны отдельная роль миграций, рабочая роль с ограниченными правами и политики доступа предприятия; текущий сервер защищает доступ через API и работает как владелец схемы.
