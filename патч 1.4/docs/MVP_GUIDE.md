# Руководство по MVP «НарядAI»

Кейс №1 АО «Костанайские Минералы». Основа — `cloud-1.4` и исправление айдентики
`fc9022a`. Пользователь разрешил демонстрационные данные. Соответствие требованиям:
[CASE_ALIGNMENT.md](CASE_ALIGNMENT.md).

## Запуск локального веб-показа

1. Распакуйте проект и выполните `install_web.bat` из `патч 1.4`.
2. Запустите `start_web.bat`. Оставьте окно сервера открытым.
3. Откройте `http://127.0.0.1:8841` в браузере и выберите роль.
4. Для завершения нажмите `Ctrl + C` в окне сервера.

Эквивалентная команда из папки проекта:

```powershell
.webvenv\Scripts\python.exe run_demo.py
```

Браузерный установщик создаёт `.webvenv` без Qt; его установка на этом компьютере
отдельно не проверялась. `start_web.bat` использует это окружение, а при его отсутствии
поддерживает ранее созданную `.venv`. Вручную:

```powershell
py -3.12 -m venv .webvenv
.webvenv\Scripts\python.exe -m pip install -r requirements-server.txt
.webvenv\Scripts\python.exe run_demo.py
```

Данные этого запуска: `demo_data/naryadai.db` и `demo_data/photos`. ИИ отключён:
отчёты сразу поступают мастеру. Облачные настройки и данные настольного клиента
не нужны. Старые базы не удаляются и не дополняются автоматически новыми аккаунтами.
Для чистого демонстрационного набора укажите новую папку:

```powershell
start_web.bat --data-dir demo_data_new
```

Настройка Render, Supabase и AnythingLLM сохранена в [README](../README.md).
`start.bat` открывает локальный Qt-клиент; `start_client.bat` — Qt-клиент
общего настроенного сервера. Веб-интерфейс общего сервера открывается по его адресу.

## Телефон и установка PWA

По умолчанию демо доступно только на компьютере. Для проверки интерфейса в браузере
телефона в той же локальной сети:

```powershell
start_web.bat --host 0.0.0.0 --port 8841
```

На телефоне откройте `http://IP_КОМПЬЮТЕРА:8841`, указав локальный IPv4 компьютера
из `ipconfig`. Windows может запросить доступ Python в частной сети. Этот режим
с тестовым паролем предназначен для локального показа; публичный сервер описан
в README.

Открытие по HTTP в локальной сети ещё не подтверждает установку PWA. Для установки
на телефоне и работы service worker нужен подходящий HTTPS-доступ. В коде есть
manifest, иконки и кнопка установки, появляющаяся, когда браузер предлагает установку.
На настоящем Android установка, запуск с домашнего экрана и камера пока не проверены.
APK не создаётся.

## Аккаунты и данные

| Роль | Логины чистой локальной базы | Пароль |
|---|---|---|
| Мастер | `master`, `master2` | `1234` |
| Сотрудник | `worker1`–`worker15` | `1234` |
| Администратор | `admin` | `1234` |

Выберите соответствующую роль при входе. Для нового назначения удобен `worker4`:
у него нет начатого демо-наряда. В облаке начальный пароль берётся из
`BOOTSTRAP_PASSWORD`; сохранённые пользователи и пароли при обновлении не заменяются.

На чистой базе создаются 4 участка, 25 единиц оборудования, 3 бригады, 20 шифров,
40 материалов, 4 условных норматива, 15 сотрудников и 2 мастера. Люди, оборудование
и нормативы демонстрационные. Цены материалов равны нулю и требуют заполнения.
Новые шифры распределены по демонстрационным классам М/Э/Г/П/С; реальный
классификатор предприятия нужно получить у организаторов. Старые коды D в
сохранённой истории остаются без переименования.
По умолчанию загружается небольшой набор. Для 540 синтетических исторических
нарядов за 90 дней запустите отдельный режим:

```powershell
start_web.bat --history --data-dir demo_history_data
```

Генератор отказывается менять существующую непомеченную базу. Повторный запуск
уже помеченной демо-истории не дублирует записи. Отдельная команда
`.webvenv\Scripts\python.exe tools/demo_history.py --data-dir demo_history_data`
требует новую пустую папку и создаёт данные без запуска сервера.

Четыре заранее заложенных сценария: износ подшипника конвейера, неисправность
датчика грохота, загрязнение аспирации, утечка гидравлического масла насоса.
Это вручную спроектированные синтетические закономерности для демонстрации
аналитики, а не открытия модели или реальные поломки. Фото и ответы ИИ не
подделываются. Исторические отчёты имеют явные пометки демо и ручной приёмки.

Администратор добавляет и редактирует справочники. Отключение сохраняет историю;
нельзя отключить участок с действующим оборудованием или элемент, нужный текущим
работам. В старых нарядах сохраняются прежние названия. При новой выдаче оборудование
выбирается из действующего справочника соответствующего участка.

## Сценарий мастера

1. На главной странице оцените приёмку, аварийные работы, сроки и загрузку сотрудников.
2. Нажмите «Выдать наряд». Выберите участок и связанное с ним оборудование.
3. Заполните название, описание, тип, приоритет, плановое время, день, начало и срок.
   Выберите ответственного исполнителя.
4. При необходимости выберите бригаду: ответственный должен входить в неё. Норматив
   служит ориентиром; фактические часы сотрудник укажет в отчёте.
5. Сохраните. Статус «Выдан» требует ответа сотрудника. Сервер проверяет смену,
   пересечения и завершение запланированной работы до срока.
6. После отказа прочитайте причину и переназначьте работу. Начатые наряды этим
   действием передавать нельзя.
7. Откройте отправленный отчёт: задача, результат, материалы, фотографии, проверки
   и доступная рекомендация ИИ показаны вместе.
8. Примите со своей оценкой 0–100 либо верните на доработку. Для решения нужен
   комментарий; ИИ сам не принимает работу.

В настольном клиенте мастер также настраивает смены и график команды. Самовыбор
сотрудником старых «Доступных» задач сохранён как дополнительный сценарий.

## Сценарий сотрудника

1. На странице смены откройте наряд: статус и срочность показаны отдельно.
2. Примите, поместите в очередь или откажитесь с объяснением.
3. Начните работу. При остановке укажите причину паузы; затем продолжите.
4. В отчёте опишите действия и результат контрольной проверки, фактические часы,
   шифр неисправности и использованные материалы.
5. Приложите до 3 фото JPG, PNG или WebP, до 8 МБ и 40 Мп каждое. Для внепланового
   наряда обязательно фото результата после выполнения. Оригинал сохраняется.
6. Отправьте. Ожидание ИИ и мастера не считается активной работой.
7. При возврате прочитайте комментарий, доработайте и отправьте новый отчёт;
   предыдущий сохраняется как предыдущая версия.
8. После приёмки посмотрите оценку и отзыв мастера в собственных результатах.

Этапы: «Выдан» → «Принят исполнителем» / «В очереди» → «В работе» ↔ «Приостановлен»
→ «Проверяет ИИ» при подключённой модели → «На проверке» → «Принят» либо «Доработка».
Отказ и отмена отдельны. Старый статус «В графике» поддерживается для совместимости.

## Черновики и связь

Отчёт сохраняется локально. В браузере IndexedDB хранит форму и выбранные фотографии
с привязкой к пользователю и наряду. В Qt локальные файлы привязаны к серверу,
пользователю и наряду; при восстановлении проверяется доступность исходных фото.
Успешная отправка удаляет черновик; выход очищает локальные черновики клиента.

При неопределённом ответе сервера PWA сохраняет отправленный запрос и позволяет
повторить его: сервер защищает от создания второго отчёта. Автоматической фоновой
отправки и полноценной работы без сети нет. Service worker кэширует публичную
оболочку, а не ответы API или фотографии отчётов. Получение нарядов и серверных
фото, отправка и приёмка требуют связи.

## Приоритеты и уведомления

| Приоритет | Код | Непринятие |
|---|---|---|
| Аварийный | `urgent` | Через 3 минуты |
| Высокий | `high` | Через 10 минут |
| Обычный | `normal` | Через 10 минут |
| Плановый | `routine` | Через 10 минут |

За 30 минут до срока появляется напоминание; после срока — просрочка. Уведомления
сохраняются в БД и переживают перезапуск. «Прочитано» относится к пользователю
и не исправляет причину предупреждения. До начала смены отсчёт принятия не идёт.
Время предприятия трактуется как `Asia/Qyzylorda`.

Пороги меняет администратор в настольном экране уведомлений. Уведомления внутри
приложения; внешних push/SMS нет. После отправки в `submitted` или `aiPending`
контроль выполнения прекращается; возврат на доработку возобновляет его.
Периоды активной работы отделены от пауз и ожидания проверки.

## Фото, ИИ и решение мастера

Сервер проверяет пригодность файла, время EXIF при наличии, точный повтор SHA256
и приблизительное сходство. Замечания привязаны к полям; мастер открывает доступный
источник совпадения. Сотруднику не передаётся информация о чужом отчёте. Отсутствие
EXIF и сходство требуют проверки контекста, а не доказывают нарушение.

Подробнее: [PHOTO_CHECKS.md](PHOTO_CHECKS.md). Для старых облачных фото без сохранённых
метаданных проверка повторов может быть неполной; это явно сообщается.

При настроенном сервере AnythingLLM даёт предварительную оценку, замечания
и критерии. Модель задаётся в AnythingLLM; Qwen автоматически не загружается.
Сервер проверяет формат, мастер задаёт итоговую оценку. Сбой модели или недоступный
обработчик ведут к ручной проверке по правилам README. Локальное веб-демо работает
без модели. Тестовый ответ подтверждает программный маршрут, а не качество модели.

Чат администратора с AnythingLLM доступен в настольном клиенте. Он не получает
автоматически всю БД и не меняет наряды. Веб-MVP сосредоточен на выдаче, выполнении,
приёмке и справочниках.

## Аналитика и граница готовности

Мастер видит загрузку, приёмку, срочные работы и предупреждения. Карточка оборудования
собирает историю, последние результаты, повторные шифры и паузы с причинами.
Статистика сотрудников опирается на принятые отчёты и оценки мастера.

Интервалы фиксируются действиями пользователя. Пауза по наряду не равна подтверждённому
простою оборудования. Финансовый эффект и процент сокращения простоев не заявляются.

Настоящие PostgreSQL, Render/Supabase, модель AnythingLLM, Android-установка и камера
требуют отдельного прогона. Нужно измерить скорость выдачи (≤1 минуты / ≤6 нажатий),
обновления и загрузки на реальной сети. 540 демонстрационных нарядов не заменяют
настоящую историю и доказанные закономерности. Фото исходной проблемы при выдаче,
структурированные специальности/разряды и vision-сравнение до/после ещё не реализованы.
APK и автоматическая offline-очередь в текущую версию не входят.
