# НарядAI 1.4 — АО «Костанайские Минералы»

Кейс №1 QOSTANAI AI INDUSTRY HACKATHON 2026. Заказчик — АО «Костанайские Минералы».

Последнее обновление команды `bc42975` с отдельным пакетом `database/` включено
в ветку. Пакет рассчитан на прежний workflow; перед подключением к этому MVP
нужна [отдельная интеграция схемы и справочников](docs/DATABASE_COMPATIBILITY.md).
Для текущего локального показа используйте `run_demo.py`, как описано ниже.
Рабочий прототип: мобильный веб-интерфейс/PWA и настольный Python/PySide6-клиент
используют общие серверные правила. Для облака предусмотрены Render, PostgreSQL
Supabase, приватное хранилище фото и AnythingLLM на домашнем ПК.

Основной путь: мастер выдаёт наряд → сотрудник принимает и выполняет → отправляет
фотоотчёт → ИИ даёт рекомендацию, если подключён → мастер принимает или возвращает
работу. Реализованы связанные справочники, четыре приоритета, очередь, отказ с
причиной, паузы, уведомления, черновики и история оборудования.

Сценарии и ограничения: [docs/MVP_GUIDE.md](docs/MVP_GUIDE.md).
Соответствие кейсу: [docs/CASE_ALIGNMENT.md](docs/CASE_ALIGNMENT.md).

## Быстро посмотреть мобильный веб-интерфейс

Запустите `install_web.bat`, затем `start_web.bat` и откройте
`http://127.0.0.1:8841`. Эквивалентная команда:
`.webvenv\Scripts\python.exe run_demo.py`. Браузерный установщик ставит серверные
зависимости без Qt; его запуск на этом компьютере отдельно не проверялся.

Это отдельное локальное демо: SQLite и фотографии находятся в `demo_data`,
ИИ отключён; отчёты сразу поступают мастеру для ручной приёмки.
Render, Supabase, Ollama и AnythingLLM для этого запуска не нужны. Данные
настольной версии и настроенного облака не пересоздаются.

На чистой базе: логины `master`, `master2`, `worker1`–`worker15`, `admin`;
пароль `1234`, роль выбирается при входе. Для сквозного показа удобен `worker4`.
Существующая демо-база автоматически не дополняется новыми аккаунтами; для нового
набора запустите `start_web.bat --data-dir demo_data_new`.

Для аналитики доступна отдельная синтетическая история:
`start_web.bat --history --data-dir demo_history_data`. Только новая папка либо
уже помеченная этим генератором база: 540 нарядов за 90 дней, четыре заранее
заложенных сценария повторных неисправностей. Фотографии и ответы ИИ не имитируются.

Для браузерной версии достаточно окружения с `requirements-server.txt`;
настольной версии дополнительно нужен PySide6 из `requirements.txt`.
Проверка в браузере телефона по локальной сети и установка PWA — разные действия:
инструкция и условия HTTPS приведены в [руководстве MVP](docs/MVP_GUIDE.md).
APK не собирается, автоматической очереди отправки без сети нет. Установка на
настоящем Android, реальные PostgreSQL/Render и подключение настоящей модели
AnythingLLM в этой доработке ещё не проверены.

## Установка на Windows: короткая папка

Распакуйте чистый архив в короткую папку, например
`C:\Users\ВашеИмя\NaryadAI`, и запустите `install.bat` из папки `патч 1.4`.
Не вкладывайте несколько папок из распакованного архива друг в друга:
PySide6 содержит файлы с длинными именами, и полный путь может превысить
обычный предел Windows. Установщик проверяет длину пути до создания `.venv`.

Если pip уже сообщил `No such file or directory` с подсказкой `Windows Long Path
support`, распакуйте архив заново в короткую папку и повторите установку.
Не переносите частично созданную `.venv`; виртуальное окружение создастся снова.
База приложения в папке данных Windows не удаляется. Установщик не меняет реестр.

`py -3 tools/install.py --check` проверяет путь без установки пакетов.
После установки `start.bat` открывает локальный настольный клиент,
`start_web.bat` — отдельное браузерное демо, `start_client.bat` подключает
настольный клиент к настроенному общему серверу.

## Схема работы

Клиенты сотрудника и мастера подключаются по HTTPS к одному серверу Render.
Сервер хранит пользователей, задачи, отчёты и очередь ИИ в PostgreSQL Supabase,
фотографии — в приватном Supabase Storage. Секреты базы клиентам не передаются.
Домашний `worker.py` сам подключается к Render и забирает отчёты. Он обращается
к локальному AnythingLLM, получает структурированный ответ и отправляет его серверу.
Публичный вход к домашнему ПК, VPN и открытие портов роутера не нужны.

ИИ даёт предварительную оценку 0–100, замечания и оценки четырёх критериев.
Сервер проверяет формат, диапазоны и сумму. Мастер принимает работу/возвращает
на доработку и назначает окончательную оценку. Рейтинг считается по оценке мастера.
Название модели выбирается в AnythingLLM; приложение не закрепляет конкретную модель.
Обязательные проверки фотографий выполняются детерминированно до ответа модели:
валидность, метаданные времени, SHA256 и приблизительное визуальное совпадение.
Повтор и отсутствие EXIF — замечания для проверки мастером, а не доказательство
нарушения. Подробности: [docs/PHOTO_CHECKS.md](docs/PHOTO_CHECKS.md).

Если `AI_ENABLED=false`, новые отчёты сразу идут мастеру. Это настройка Environment
Render с перезапуском сервиса; кнопка администратора ещё не добавлена.
Если домашний обработчик не подключён, отчёт ждёт до 120 секунд, затем поступает
мастеру. Активная проверка имеет срок 11 минут; если ПК отключился во время неё,
по истечении срока доступна ручная проверка. Некорректный ответ модели сразу
передаёт отчёт мастеру с объяснением. Очередь и её состояние переживают перезапуск.

## Развернуть облачный сервер

В репозитории используется отдельная папка `патч 1.4`; основа — ветка `cloud-1.4`.
Для развёртывания выбирайте ветку, в которую вошли доработки MVP; до слияния
изменений исходная `cloud-1.4` может содержать предыдущую версию.
Этот исходный код ещё не означает, что сервис уже развёрнут: рабочий адрес появляется
только после успешного запуска Render и проверки подключений к вашему Supabase.

1. В Supabase выбрать отдельный бесплатный проект для теста либо существующий
   проект. Сервер создаёт только схему `naryadai` и приватный бакет `naryadai-reports`.
   Существующие таблицы `public` не изменяются. Новая облачная база получает тестовые
   аккаунты и данные; автоматического переноса прежней SQLite-базы нет.
2. В Supabase **Connect → Session pooler** скопировать строку подключения
   PostgreSQL, порт 5432. Этот вариант подходит для постоянного сервера через IPv4.
   Вставить пароль БД; специальные символы в URL-пароле должны быть закодированы.
   Добавить `?sslmode=require` (либо `&sslmode=require`, если параметры уже есть).
   Не путать пароль БД с API-ключом. Режим Transaction pooler для этого проекта
   не выбирать: сервер использует сессионные настройки внутри транзакций.
3. В **Settings → API Keys** взять secret key `sb_secret_...`; также поддержан
   прежний JWT `service_role`. Publishable/anon key не подходит для серверного Storage.
   В **Settings → Data API** взять Project URL вида `https://PROJECT.supabase.co`.
4. На Windows установить Python 3.12 (64 бит), распаковать проект, запустить
   `install.bat`, затем `generate_cloud_secrets.bat`. Файл `cloud-secrets.txt`
   содержит два различных случайных секрета. Он исключён из GitHub; в чат его не отправлять.
5. В Render создать **Web Service**, выбрать `MrAngelskye/hakaton`, ветку
   `cloud-1.4`, **Root Directory: `патч 1.4`**, **Runtime: Python**, **Free**,
   регион Frankfurt. Build Command: `pip install -r requirements-server.txt`,
   Start Command: `python run_server.py`, Health Check: `/health`.
   Также приложен `render.yaml` для Blueprint; путь к нему `патч 1.4/render.yaml`.
6. В **Environment** Render внести значения из таблицы ниже. Сохранить и запустить
   развёртывание. Адрес вида `https://ИМЯ.onrender.com` скопировать после успеха.
   По `/health` должен вернуться JSON `ok: true`, `version: 1.4`.

| Переменная Render | Значение |
| --- | --- |
| `DATABASE_URL` | Строка Session pooler с паролем БД и `sslmode=require` |
| `SUPABASE_URL` | Project URL |
| `SUPABASE_SECRET_KEY` | Secret key либо legacy service_role |
| `AI_WORKER_TOKEN` | Из `cloud-secrets.txt`; только для домашнего обработчика |
| `BOOTSTRAP_PASSWORD` | Из `cloud-secrets.txt`; начальный пароль тестовых аккаунтов |
| `AI_ENABLED` | `true` для ИИ, `false` для ручной проверки |
| `PYTHON_VERSION` | `3.12.13` |
| `TZ` | `Asia/Qyzylorda` |

Если сервис создаётся через подключение без Root Directory, команды такие:
`cd 'патч 1.4' && pip install -r requirements-server.txt` и
`cd 'патч 1.4' && python run_server.py`. Сервер не устанавливает графический Qt;
настольные клиенты используют прежний PySide6. Dockerfile оставлен как запасной способ.

`PORT` задаёт Render автоматически. Ничего из перечисленных секретов не вносить
в исходники, GitHub, архив для товарища или публичный `client_config.json`.
При изменении `BOOTSTRAP_PASSWORD` существующие пароли не заменяются: это параметр
первоначального создания. Менять пароли аккаунтов можно под администратором в приложении.

## Настроить ИИ на своём Windows-ПК

1. Установить Ollama: https://ollama.com/download/windows. Скачать подходящую
   локальную модель командой `ollama pull ИМЯ_МОДЕЛИ`. Модель должна надёжно выдавать
   JSON по инструкции; качество оценок проверяется на ваших реальных отчётах.
2. Установить AnythingLLM Desktop:
   https://docs.anythingllm.com/installation-desktop/windows.
   Выбрать локальный **LLM Provider → Ollama**, адрес `http://127.0.0.1:11434`,
   скачанную модель. Оставить обе программы запущенными.
3. В AnythingLLM **Developer API** создать ключ. Локальная документация обычно
   `http://127.0.0.1:3001/api/docs`. Ключ вводится только на своём ПК.
4. В проекте после `install.bat` запустить `configure_server.bat`: указать локальный
   адрес API, скрытым вводом ключ, подпись модели, фотографии для первого теста
   отключить. Выбрать **0 — создать отдельное пространство**. Остальные параметры
   можно оставить; локальную базу обработчик не использует.
   Скрипт также создаст **НарядAI — чат администратора**, отдельный от оценивания
   отчётов. Для обоих пространств в AnythingLLM должна быть выбрана ваша модель.
5. Запустить `check_ai.bat`. Успех: модель ответила, формат и сумма оценок проверены,
   затем получен обычный текстовый ответ чата.
   Это реальный запрос к вашей модели. Ошибку сначала исправить в AnythingLLM.
6. Запустить `configure_worker.bat`: указать адрес Render и скрытым вводом
   `AI_WORKER_TOKEN` из своих секретов. Скрипт проверит доступ и сохранит конфигурацию.
7. Открыть `start_worker.bat` и оставить окно открытым. ПК должен быть включён,
   без сна, AnythingLLM и Ollama — запущены. `start_server.bat` для облака не требуется.
   Фото включать только при проверенной поддержке изображений моделью/API.

## Подключить два приложения

На обоих ПК: распаковать проект, выполнить `install.bat`, открыть `start_client.bat`.
Первый раз ввести один и тот же HTTPS-адрес Render; он сохранится в `client_config.json`.
Дальше приложение подключается автоматически. Для смены адреса — `configure_client.bat`.
Ожидание первого ответа после простоя бесплатного сервера предусмотрено в запуске.

Один входит под `master`, другой под `worker4`, выбрав соответствующие роли.
Начальный пароль — `BOOTSTRAP_PASSWORD`, заданный владельцем сервера. Сначала изменить
тестовые пароли через администратора. `1234` используется только в локальном демо.
Для товарища достаточно исходного чистого архива; AnythingLLM ему не нужен.
Если передаёте копию своей настроенной папки, удалите из копии `server_config.json`,
`worker_config.json`, `cloud-secrets.txt`, `.env`, базы и фотографии. Публичный адрес
в `client_config.json` можно оставить, тогда вводить его товарищу не придётся.

Сценарий проверки: мастер выдаёт наряд на свободное время смены worker4, выбирая
участок и связанное оборудование; сотрудник принимает, начинает, при необходимости
приостанавливает с причиной, продолжает и отправляет отчёт. Для внеплановой работы
нужно фото результата. Если обработчик подключён, в его окне появляется номер
отчёта, у мастера — результат ИИ; при отключённом ИИ доступна ручная приёмка.
Мастер выставляет свою оценку; сотрудник видит её после обновления. Списки обновляются
примерно раз в 3 секунды. Проверка ИИ не блокирует окно отправки отчёта.

## Чат администратора с ИИ

В настольном клиенте войдите под ролью **Администратор**, логин `admin`, и откройте **Чат с ИИ**.
Напишите вопрос и нажмите **Отправить** или **Ctrl + Enter**. Обычный чат и
оценка отчётов используют разные пространства AnythingLLM. История каждого
администратора отдельная и сохраняется на сервере; **Новый чат** начинает диалог
без предыдущего контекста. На экране видны последние 100 обращений, в контекст
модели передаются до 6 предыдущих ответов с ограничением объёма.

На Render задайте `AI_ENABLED=true`, выполните **Save, rebuild, and deploy**.
Если сервис приостановлен, сначала нажмите **Resume**. Должна использоваться
опубликованная версия с этой доработкой. Root Directory и команды должны совпадать
с выбранным выше способом развёртывания: при `Root Directory: патч 1.4` —
`pip install -r requirements-server.txt` и `python run_server.py`; вариант с пустым
Root Directory уже описан выше. Настройка одного чата не меняет путь запуска сервера.

Пока на домашнем ПК открыты AnythingLLM, Ollama и `start_worker.bat`, сервер
передаёт туда вопросы и отчёты. Открывать порты роутера не нужно. API-ключ
AnythingLLM остаётся в `server_config.json` только на ПК с ИИ; клиентам и Render
он не нужен. Отключённый ПК, ошибку модели или таймаут чат показывает явно.
При потере связи повторная отправка того же сообщения защищена от дублирования.
ИИ не получает автоматически всю базу и не меняет задачи: вставьте в чат текст,
который хотите обсудить. Окончательное решение по отчётам принимает мастер.

Проверка нового маршрута: `python tests/check_admin_chat.py`.

## Данные и права

Схема `naryadai` закрыта для PUBLIC, на всех её таблицах включён RLS без публичных
политик. Настольные и браузерные клиенты общего сервера работают через API; роли проверяются сервером
по сессии, а не по выбранной кнопке клиента. Бакет приватный: сервер проверяет право
на каждый отчёт перед выдачей фото. Секрет ИИ не заменяет пользовательскую сессию.

| Таблица | Что хранится |
| --- | --- |
| `users` | Аккаунты, роли, активность, соль и хеш пароля |
| `tasks` | Наряды, исполнитель/бригада, сроки, статусы и фактические отметки времени |
| `reports` | Текст, материалы, время, фото, детерминированные проверки и оценка мастера |
| `events`, `pauses` | История и причины/периоды остановок |
| `work_sessions` | Интервалы активной работы без пауз и ожидания проверки |
| `reference_items` | Участки, оборудование, бригады, шифры, материалы, нормативы |
| `workflow_settings`, `task_alerts`, `alert_acknowledgements` | Параметры, постоянные уведомления и отметки прочтения |
| `shift_rules`, `shifts` | Шаблон смены и исключения на дату |
| `ai_jobs`, `ai_worker_state` | Оценка ИИ, очередь, состояние обработчика |
| `chat_conversations`, `chat_requests` | Личные диалоги администраторов, сообщения и очередь чата |
| `sessions`, `rpc_results` | Хеши сессий и защита от повторного запроса |

Рейтинг вычисляется из принятых отчётов; отдельной таблицы рейтинга нет.
Короткие транзакции сериализуются общим PostgreSQL advisory lock для теста вдвоём.
Масштабирование на большое предприятие требует отдельной работы.

## Бесплатные тарифы и проверки

На бесплатном Render возможны остановка по неактивности и задержка первого ответа;
актуальные условия нужно сверить с тарифом. Служебный обработчик посылает heartbeat, пока открыт.
Файловая система Render временная, поэтому БД и фото вынесены в Supabase.
Лимиты Supabase Free и паузу проекта при неактивности учитывать по текущему тарифу.

Установка тестовых зависимостей: `python -m pip install -r requirements-test.txt`.
Проверки: `tests/check_app.py`, `check_schedule.py`, `check_server.py`,
`check_live_server.py`, `check_cloud.py`, `check_storage.py`, `check_headless_server.py`,
`check_mvp_workflow.py`, `check_photo_checks.py`, `check_mvp_api.py`, `check_demo_history.py`.
Последняя проверка запускается в отдельном окружении только с серверными
зависимостями и httpx; она проверяет HTTP, фото и ручную оценку без Qt.
Облачный тест действительно запускает HTTP-сервер, два клиента и обработчик, но
использует тестовый HTTP-ответ AnythingLLM. Качество настоящей модели он не доказывает.
Для `TEST_DATABASE_URL` допускается только локальная тестовая база: тесты пересоздают
схему `naryadai`. В этой доработке серверные сценарии проверяются на временных
SQLite-базах с тестовым ответом AnythingLLM. Ранее проверявшийся PostgreSQL-совместимый
PGlite не подтверждает текущие миграции на настоящем PostgreSQL. Реальный PostgreSQL,
развёртывание Render/Supabase, настоящая модель и установка на Android требуют
отдельного интеграционного прогона. 540 нарядов за 90 дней доступны только как
явно синтетическая история; реальные производственные данные пока не получены.

Локальный режим сохранён: `start.bat` — отдельное демо; `start_server.bat` — прежний
локальный сервер после настройки, SQLite и локальный AnythingLLM. Не путать с облаком.

Официальные инструкции: https://render.com/docs/free,
https://supabase.com/docs/guides/database/connecting-to-postgres,
https://supabase.com/docs/guides/storage/serving/downloads,
